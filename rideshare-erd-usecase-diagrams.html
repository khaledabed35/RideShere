RideShare — Entity Relationship & Use Case Diagrams

Derived from the actual C# domain model (ASP.NET Core Identity, EF Core, PostGIS, Paymob). Diagrams reflect confirmed foreign keys and flag ambiguities rather than inventing constraints.

A. Entity Relationship Diagram (ERD)

The system uses ASP.NET Core Identity — App_User inherits IdentityUser<Guid>, so it is the base identity table for all roles (Passenger, Driver, Admin). DTOs (RegisterModel, LoginModel, ForgetPasswordConfirm, AuthModel) and enums are intentionally excluded as tables.

Major relationships

  • App_User → Driver (1:1, identity specialization): Driver.Id is both PK and FK to App_User.Id — a driver is a user with an extended profile, sharing the same Guid.
  • App_User → AddressModel, Notification, Trip, Review (1:N): a user can save multiple addresses, receive many notifications, request many trips as a passenger, and author many reviews.
  • Driver → DriverDocument (1:1): the driver's onboarding/verification packet (license, national ID, car photos) tied to one driver.
  • Driver → Car (1:N): cars carry DriverId as FK; a driver can be linked to multiple car rows in the schema as written.
  • Driver → Offer, Trip, Payout (1:N): a driver submits many offers, participates in many trips (nullable FK on Trip), and receives many payouts.
  • Trip → Offer, TripStatusLog (1:N): a trip collects multiple driver offers and logs every status transition.
  • Trip → Payment (1:0..1): a trip optionally has one payment record as modeled.
  • Trip → Car (0..1): a trip may optionally reference the assigned car once a driver/offer is accepted.
  • Payment → Payout (1:N): a payment can fund one or more payout records to the driver.

B. Use Case Diagram

Actors: Passenger, Driver, and Admin are primary human actors; Paymob is an external system actor reached only through the payment flow. The diagram below shows the core use cases and their <<include>> / <<extend>> relationships; the complete use-case inventory per actor follows in the tables beneath it.

Main business flows

  • Ride request → offer → acceptance: passenger requests a ride (includes pickup/dropoff selection, fare estimate, payment method); the request is exposed to nearby drivers; drivers submit priced offers; the passenger accepts one, which assigns the driver (and its car) to the trip and sets the agreed fare.
  • Trip execution: the driver updates trip status (arrived → in progress → completed); each transition is written to the trip status log; the passenger tracks progress in real time.
  • Payment: on completion, the passenger pays by cash or through Paymob; Paymob-based payments hand off to the external gateway for processing, and a webhook updates the payment status asynchronously.
  • Driver verification: a new driver submits documents (national ID, license, car license); an admin reviews and approves or rejects them with a reason before the driver can go online.
  • Post-trip: the passenger rates the driver and can leave a review; the driver accrues earnings that are later paid out.
  • Cancellation is modeled as an alternative flow off Request Ride / Update Ride Status, available to both passenger and driver up to certain trip states.

C. Validation & Inconsistencies

Before finalizing, these points in the provided C# model deserve explicit attention rather than a silent fix:

AreaObservationStatus
Review.DriverId Present as a Guid property, but no navigation property or [ForeignKey] attribute is shown. EF Core will not create a relational FK constraint for it unless configured (Fluent API or attribute). Drawn in the ERD as a plain reference, not a modeled relationship. Inferred
Notification.TripId / OfferId Both are nullable Guids with no explicit FK configuration shown. Treated as optional soft-references in the ERD, not enforced foreign keys, until confirmed in OnModelCreating. Inferred
Payment.TripId cardinality TripId is required on Payment, but whether the database allows multiple Payment rows per Trip (e.g. retries) depends on whether a unique index/constraint is placed on TripId. Modeled as 1 : 0..1 per the stated business rule, but this must be verified against the actual EF configuration. Inferred
Driver → Car cardinality Car.DriverId exists as an FK, but Driver is not shown with a Cars collection navigation property. The FK direction confirms Car belongs to a Driver; whether one driver can legitimately register more than one car is a business rule that isn't enforced by a unique constraint in what was provided. Confirmed FK / Cardinality inferred
DriverDocument uniqueness Conceptually one document set per driver, but nothing in the provided model guarantees a unique constraint on DriverDocument.DriverId. Without it, the "1:1" is only a convention, not an enforced database rule. Inferred
Payout.PaymentId cardinality PaymentId is required on Payout, and the ERD models Payment 1 : N Payout (e.g. partial/split payouts), but this depends entirely on EF Core configuration not shown here. Inferred
Confirmed from the C# model: App_User↔Driver (shared Guid PK/FK), AddressModel→App_User, Car→Driver, Offer→Trip & Offer→Driver, TripStatusLog→Trip, Trip→App_User (passenger).
Needs EF Core verification before treating as a hard constraint: Review→Driver, Notification→Trip/Offer, Payment→Trip cardinality, DriverDocument uniqueness, Payout→Payment cardinality.

Infrastructure notes

  • PostGIS / NetTopologySuite — Trip.PickupLocation and DropoffLocation are geography Point columns, not separate tables.
  • Redis — used for real-time/location data (e.g. nearby-driver lookups), intentionally excluded from the relational ERD since it isn't a relational store.
  • JWT / Refresh tokens — persisted as plain columns on App_User (RefreshToken, RefreshTokenExpireTime), not a separate token table.
  • Paymob — appears only as an external actor and as gateway-identifier columns on Payment, never as a persisted domain entity.
